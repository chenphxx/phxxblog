# phxxblog技术架构与实现说明

## 1. 项目概览

phxxblog 是一个前后端分离的个人博客系统, 前台与管理后台共用同一套 REST API 

## 2. 技术栈

| 层     | 技术                                                                                                                          |
| ------ | ----------------------------------------------------------------------------------------------------------------------------- |
| 前端   | Vue 3, TypeScript, Vite, Vue Router(hash 模式), Pinia, Axios, Element Plus, Vditor                                            |
| 后端   | Python 3.10+, FastAPI, SQLAlchemy 2.x(声明式 ORM), Pydantic v2 / pydantic-settings, PyMySQL, PyJWT, bcrypt, feedgen, Markdown |
| 数据库 | MySQL(utf8mb4 / utf8mb4_unicode_ci)                                                                                           |
| 其他   | ip2region 离线 IP 库(vendored, 可选)                                                                                          |

**没有引入数据库迁移工具**: 新表由启动时的建表动作创建, 已有表加列需要手工写迁移 SQL 并登记 应用启动会校验模型与库结构是否一致, 缺列则拒绝启动 

## 3. 系统架构

```text
浏览器 (Vue3 SPA: 博客前台 + 管理后台, Pinia 状态 / Axios 请求 / Element Plus 组件)
   │
   │  Axios → /api/v1/**          上传与静态资源 → /assets/**
   ▼
Vite 开发代理(frontend/vite.config.ts, 仅开发环境)
   │  /api  /assets  /docs  /redoc  /openapi.json  →  http://localhost:8000
   ▼
FastAPI(backend/app/main.py)
   ├─ modules   模块体系: 每个能力一个包(spec 元数据 + router 接口) + 注册表/装配
   ├─ core      配置, 安全(JWT/bcrypt), 权限码, 中间件, 统一响应
   ├─ services  业务服务(渲染 / 上传 / 统计 / 导入导出 / 文章查询与写入等)
   ├─ models    SQLAlchemy 模型        ├─ schemas  Pydantic 请求与响应模型
   ▼
MySQL(SQLAlchemy + PyMySQL); 上传文件落盘在 assets/, 由 /assets 静态目录对外提供
```

### 3.1 请求链路

1. 前端统一通过 Axios 实例请求 `/api/v1/**`, 开发环境由 Vite 代理到后端; 上传与静态资源走 `/assets/**` 
2. 请求拦截器自动附带 `Authorization: Bearer <access_token>`, 令牌存于 localStorage 
3. 后端通过 FastAPI 依赖注入完成"取当前用户 -> 校验权限 -> 提供数据库会话" 
4. 所有接口返回统一结构 `{ code, message, data }`, 前端响应拦截器解出 `data` 供业务代码直接使用 
5. 上传文件落盘到仓库根目录的 `assets/uploads/<年>/<月>/`, 再由后端的 `/assets` 静态目录对外提供访问

### 3.2 运行形态

- **开发**: 后端 uvicorn(--reload) + 前端 Vite, 直接运行根目录 `start.bat` 即可 
- **生产**: 前端构建产物交给静态服务器, 后端独立部署, 反向代理 API, 静态资源与文档路径到后端

## 5. 后端实现

### 5.1 启动与装配

- 应用入口创建 FastAPI 实例, 注册跨域与自定义中间件, 装配 API 路由与挂在根路径的路由(RSS 与 sitemap), 并把上传目录挂载为静态目录 
- 启动时先建表(幂等), 再校验模型与库结构是否一致: 缺列时调试模式只告警并打印 ALTER 语句, 否则拒绝启动 结构漂移必须在启动时暴露, 这是刻意的 
- 统一异常处理: 业务异常与参数校验失败都转成统一响应结构, 兜底异常在调试模式下直接抛出便于排查 
- 路由是由模块注册表装配(见 5.7)

### 5.2 配置管理

- 基于 pydantic-settings, 从环境变量或 `backend/.env` 读取, 统一前缀 `PHXXBLOG_`, 以单例提供 全部配置项与默认值见 `backend/.env.example` 
- 安全相关的两条硬约束: 签名密钥使用仓库占位值或长度不足会拒绝启动; 只有来自可信代理配置的请求才采信转发头, 否则一律使用 TCP 直连地址 否则客户端可以伪造 IP, 会影响点赞去重, 游客评论归属与 UV 统计 
- 默认关闭注册 个人博客开放注册等于把上传与创作能力交给任意访客 
- 初始化脚本在库中无用户时创建管理员, 密码取环境变量或随机生成并只打印一次, 不硬编码默认口令

### 5.3 数据访问

- 数据层提供 Base, engine, 请求级会话依赖与结构校验; 事务边界由请求处理函数掌握 
- **关联加载策略按"是否真的要用"逐个指定**, 改动前先读模型里的注释: 列表要序列化分类与标签, 所以用 `selectin`(多对多用 `joined` 会让分页的 LIMIT 作用在放大后的行数上, 分页结果会变少); 详情不使用的关联用 `raise`, 让误用立刻报错而不是退化成 N+1; 每次请求都要权限码的关联用 `selectin`, 而用户到文章的关联用 `select`, 避免每个需要登录的接口顺带全量拉取文章 
- 分页统一走公共分页函数, 返回结构由公共分页模型定义, 每页数量有上限且由后端兜底 
- 登录失败限流是**进程内**滑动窗口, 多 worker 或多实例部署时各自计数; 需要跨实例限流应换成 Redis 或交给反向代理

### 5.4 认证与授权

- 密码用 bcrypt 散列存储 
- 访问令牌是 JWT(默认 30 分钟), 刷新令牌是随机串且数据库只保存散列(默认 7 天, 支持吊销) 刷新令牌一次一换, 前端据此做静默续期(见 6.4) 
- 依赖注入提供"必须登录 / 允许游客 / 要求权限码"三种取用户方式, 以及兼容可信代理的客户端 IP 
- 权限模型是用户-角色-权限三层多对多, 权限码集中定义在一处 
- **一律判断权限码, 不判断角色名**: 角色标识可以被后台修改, 基于角色名的判断会在改名后静默失效或误放行 有归属的资源还会叠加"作者本人或管理员"的资源级判断

### 5.5 统一响应与分页

成功响应由统一的响应构造器生成, 失败响应由全局异常处理器生成; 两者结构一致, 前端只需处理一个分支 

```json
{ "code": 0, "message": "ok", "data": {} }
```

列表接口统一返回 `{ items, total, page, page_size }` 

### 5.6 业务服务层

服务层承载跨模块复用的业务逻辑, 模块的接口实现只做参数校验, 权限判断与响应组装 

| 类别           | 职责                                                                                        |
| -------------- | ------------------------------------------------------------------------------------------- |
| 内容处理       | Markdown 渲染为带 class 的 HTML, 文本统计, 文章查询与写入规则(状态降级与流转, 分类标签解析) |
| 媒体与外部内容 | 上传校验与落盘, 网页链接预览抓取                                                            |
| 导入导出       | 公共工具(frontmatter, 压缩包与图片地址改写)与导入管线(拆包, 解析, 查重, 落库, 写日志)       |
| 数据统计       | 访问明细与按日聚合, User-Agent 解析, IP 归属地(离线库, 缺失时降级为空)                      |
| 运维           | 操作日志写入                                                                                |

### 5.7 模块体系

一项能力(评论, 媒体库, 日记, RSS, 一言 …)就是一个模块: 一个自包含的包, 里面有元数据与接口实现, 由注册表统一登记 

```text
app/modules/
  base.py       ModuleSpec / ModuleSetting 定义(含 module.<id>.<key> 键规则与配置类型) 
  registry.py   注册表: 登记与一致性校验, 全局单例
  state.py      开关与配置的读写, 以及"真正可用"的判定
  deps.py       require_module 依赖: 模块未启用时该模块的接口返回 404
  router.py     装配: 把注册表里的模块装成 API 路由与根路径路由
  <模块 id>/    __init__.py(导入即注册) + spec.py(元数据) + router.py(接口)
```

- **分层**: 只有"接口实现"随模块走, 实体, 接口契约, 业务逻辑与配置权限是共享基础设施, 仍留在 `app/` 下供各模块复用 模块之间的边界是"能力", 不是"数据表" 
- **装配**: 用依赖判断模块是否可用, 而不是在启动时只装配启用的模块 - 后台改完开关必须立刻生效, 不能要求重启服务 锁定模块不挂该依赖以省一次查询 
- **开关**: 库里以 `module.<id>.enabled` 记录, 缺记录时用模块声明的默认值 认证, 用户, 系统设置, 模块管理, 分类标签与文章是核心能力, 不允许禁用, 关掉它们会导致后台进不去或内容不可读 扩展类模块可以声明 `default_enabled=False`, 新装环境只加载必要功能(如终端卡片, 主页简介, 个人资料卡, 页脚与 SEO 默认关闭), 已有数据库不受影响 - 开关值落在库里, 默认值只在没有记录时生效 
- **可见范围**: 库里以 `module.<id>.visibility` 记录, 取值为 `public`(所有访客都能使用这项能力)或 `admin`(仅拥有站点管理权限的账号能用), 缺记录时用模块声明的 `default_visibility` 它是比权限码更粗的一层 - 模块自己的权限码照旧生效, 可见范围只决定"这项能力要不要对访客开放": 配成 `admin` 后该模块的全部接口在模块依赖之后再挂一层可见范围依赖, 未登录 401, 已登录但无权限 403; 前台连入口与配置都拿不到 与权限码一致, 管理员按 `setting:manage` 判定, 不判断角色名 
- **可见范围分"可调"与"固定"**: 管理后台自身的内容(管理后台, 用户与角色, 系统设置, 模块管理, 媒体库, 操作日志, 后台看板)固定为 `admin`, 后台只展示不提供调整入口 - 它们的前台呈现本来就只有管理员看得到; 站点基本盘(认证, 文章, 分类标签)固定为 `public`, 真把它们锁成仅管理员, 访客侧就没有任何可读内容了 其余模块(站内搜索, 评论, 一言, 历史上的今天, 页脚, 主页简介, 个人资料卡, 日记, 更新日志, 网站链接, RSS, 外链预览, 阅读增强等)可在后台自行选择 固定值由模块声明(`locked` 或 `visibility_fixed`), 库里即使留着旧的 `visibility` 记录也不生效, 写入这些模块会被拒绝 
- **"公开"对管理员专属能力的意义**: 日记与更新日志默认只给管理员用, 它们的读取接口用"有权限码, 或模块可见范围是公开"的宽松依赖 - 配成公开后访客也能读到内容, 而写, 删, 导入导出仍然要求各自的权限码 前台的日记与更新日志入口不再写死"仅管理员", 一律由模块状态(启用 + 可见范围)决定; 对应页面在非管理员访问时隐藏新增/编辑/导入导出等管理按钮 
- **依赖**: 模块声明依赖关系, 注册时校验"存在, 不自依赖, 不成环"; 运行时判定为"自己启用且依赖链都启用" 被依赖的模块禁用时, 依赖它的模块自动视为不可用(接口 404, 前台不注册), 重新打开即恢复, 不需要级联写状态 
- **配置**: 模块用自己的配置项声明类型与取值范围, 存放于 `module.<id>.<key>`, 键在模块内唯一 上游接口地址与条数上限这类"换数据源"的差异都做成模块配置, 换数据源不必改代码 
- **配置类型**: `bool` / `int` / `text` / `long_text` / `json` / `rows` 决定后台渲染什么控件: 开关, 数字框, 单行输入框, 带 Markdown 预览的多行文本, JSON 与"按 `columns` 声明的列名逐列编辑"的行列表 多行文本与行列表占满整行, 后者支持增删行; 写入时按类型校验(整数范围, JSON 合法性, 行列表的列名与形状), 读取时容错回落到默认值 类型集合与前端 `ModuleSettingKind` 由脚本核对一致 
- **一致性校验**: 注册时拦下 id 非法或重复, 权限码不存在, 配置键重复, 整数配置缺范围等; 启动时校验依赖关系; 另有脚本核对后端注册表与前端注册表的 id 集合一致, 并检查模块权限码都进了权限表 
- **接口**: 公开接口返回"当前可用的模块 id 与模块公开配置", 前台据此决定注册哪些路由与导航; 后台接口返回完整元数据(状态, 依赖, 权限码, 配置项定义与当前值)并支持批量启停与写配置 
- **与站点级设置的分工**: 站点级设置只保留两类键 - "站点身份"(站点名/标题/描述/图标/头像/简介)是布局层与多个模块共享的输入, "平台约束"(单文件上传上限)被所有上传入口共用 某个能力的内容与开关归它自己的模块: 页脚版权与备案归 `footer`, 首页常用网站归 `sitelinks`, 主页 README 归 `about`, 社交链接与技术标签归 `profile`, SEO 关键词归 `seo` 前台区块是否展示由模块开关直接决定, 不再有第二套展示开关; 唯一的例外是访问统计 - 它是数据能力, 首页热力图只是它的一个展示面, 因此保留 `show_on_home` 配置
- **后台界面按同一分工拆开**: "模块管理"只渲染开关与元数据(有参数的功能只提示"到系统设置里配置", 不重复渲染表单), "系统设置"按"已启用且声明了参数"的功能分块展示参数 功能被禁用后它的参数不再出现, 因此"这个能力在不在"与"它怎么工作"各自只有一处入口 配置项定义里的 `columns` 也随后台接口下发, 前端的行列表编辑器据此才知道有哪些列

完整的接口清单见 `docs/接口文档.md` 

## 6. 前端实现

### 6.1 入口与样式加载

- 应用入口注册状态管理, 路由与组件库(中文语言包), 并在挂载前读取本地保存的深浅色与配色主题, 先给 `html` 打上对应类与属性, 避免首屏闪白 
- **样式引入顺序有意义**: 组件库与编辑器的样式必须先于本站的主题令牌, 否则主题无法覆盖它们 
- 编辑器与看板娘的运行时资源都自托管, 构建前由脚本从依赖目录复制, 因此运行时不依赖任何 CDN

### 6.2 路由与布局

- 使用 hash 模式便于静态托管; 全局前置守卫在"需要登录且本地无令牌"时跳转登录页并带上回跳地址 
- 前台布局由桌面侧栏(品牌区, 主导航, 次级导航, 主题与看板娘开关)与主内容区组成, 窄屏时侧栏收成抽屉 布局层负责公开配置(站点名, 标签页标题, 图标)与访问埋点 
- 后台布局是侧边菜单加顶栏, 菜单项由模块注册表生成并按权限与模块状态过滤 
- 部分前台页面使用 `keep-alive` 缓存 被缓存的组件不会重新初始化, 因此 URL 查询参数变化必须自行监听路由, 返回时的数据刷新要放在激活钩子里

### 6.3 状态管理

- **登录态**: 令牌与用户信息与本地存储同步, 登录成功时同时把令牌写入文档鉴权 cookie 令牌以 computed 形式从存储读取而不是缓存成状态, 这样静默续期改写存储后界面能立刻看到最新值 
- **外观主题**: 深浅色与配色主题是两个独立维度, 共同决定 `html` 上的类与属性并持久化; 切换时短暂加一个过渡类做颜色过渡 
- **看板娘**: 开关, 当前形象与浮层位置属于访客本地的外观偏好, 只存本地存储不下发后端; 另有一个不落盘的状态承载模块开关, 模块被禁用时连运行时与模型都不下载 
- **模块状态**: 拉取后端的可用模块集合与公开配置, 供导航, 路由守卫与首页区块判断 这份状态是按访问者生成的(仅管理员可见的模块不会下发, 连它的配置都拿不到), 所以登录与退出登录后都要强制刷新一次; 其余时候加载是幂等的 后台改完模块开关或可见范围后同样强制刷新, 导航立即跟随 登录时要在跳转前等这次刷新完成: 路由守卫正是靠它判断"目标页面所属模块对当前身份可不可用", 用匿名身份的旧集合会把后台页面挡回去 
- **"状态未就绪按可用处理"只适用于不发请求的入口**: 导航项, 品牌区这类地方这么做是为了避免首屏闪烁, 但**会自己取数的模块区块必须等状态有结果(`ready`)再挂载**(终端卡片, 首页发布记录, 历史上的今天, 评论区, 日记页的热力图) 否则区块会在模块其实已禁用的情况下先挂载并发出注定 404 的请求, 页面上就凭空多一条"模块未启用"的报错 

### 6.4 请求层

- 统一 Axios 实例, 请求拦截器附加令牌, 响应拦截器解包 `data`(文件下载除外)并统一提示错误, 同时打印一条带方法与地址的告警便于定位失败请求 
- **401 静默续期**的三条约束: 并发 401 必须共用同一个刷新请求(刷新令牌一次一换, 各刷各的会让后到的那次拿到已失效令牌); 重放过的请求与登录/刷新接口自身不再触发刷新, 避免死循环; 只有"换令牌失败"才清理会话并跳登录页, 重放失败按普通错误处理 刷新请求走不带拦截器的独立实例, 否则会递归 
- 令牌与用户信息的读写只有一处入口, 任何地方都不要写存储键字面量 散落多处时改一处名字会让其它几处静默失效, 症状是"登录成功但立刻 401" 
- 与后端对齐的请求与响应类型集中在一处, 并按业务域封装成若干接口集合

### 6.5 组件与组合式函数

- 通用组件按用途分层: 内容渲染(正文与编辑器), 列表与导航(列表行, 分页器, 相邻文章, 目录), 展示型图表(贡献热力图与访问趋势图都是纯 SVG 实现, 不引入图表库), 反馈型浮层(媒体预览, 链接卡片), 以及主题与看板娘相关控件 
- 首页的展示区块各自取数, 各自转圈, 取数失败也只影响自己那一块; 模块开关只在页面模板里判断一处, 关闭的模块不挂载因此也不会发请求 
- **跨视图重复的流程逻辑抽到组合式函数**, 视图之间的差异(接口, 文案, 单位, 取消的去向)通过 options 注入 文章编辑与导入导出返回 reactive 对象便于调用方直接读写字段, 列表分页返回一组 ref 以便与分页器双向绑定

### 6.6 样式与主题

- 视觉基调是 **Soft Minimal**: 浅灰画布加白色大面板, 靠留白与细分隔线分区, 少用卡片嵌套 前台偏阅读, 后台偏看板, 两者共用同一套颜色, 字体与控件令牌 
- **主题只声明品牌色与画布底色**(可选装饰渐变与终端强调色), 其余令牌由生成器在统一的中性基准上推导 因此换主题不会改变圆角, 阴影与字体气质, 也不会出现"换一套主题像换了一个网站" 
- 生成物分两类: 结构令牌(间距, 圆角, 阴影, 动效, 字体栈)与主题无关且只输出一份; 颜色令牌每套主题一份, 只有默认主题写裸 `:root` 以承载"新访客未选主题"的配色 改配色或改结构令牌都改源文件后重新生成, 不要手改生成物 
- **推导层的硬约定**(由自检脚本复核): 主色当文字用, 以及主色填充上的文字, 都必须与底色达到 4.5:1, 达不到时朝背景反方向逐档混合 语义色与终端令牌不随主题变化, 只区分深浅色 
- 主题令牌由样式入口统一汇总, 后台主题层必须排在所有主题之后: 它把组件库的主色与语义色令牌指向本站令牌, 并在层级上高于组件库的默认值, 否则运行期按需注入的组件样式会把它盖回去 主操作用主色(跟随品牌色), 删除与警告这类语义操作才用语义色 
- 按需引入的边界: 解析器只能识别模板里的标签, 通过 JS 调用的消息, 确认框与加载等组件样式必须手动引入, 漏了不会报错只会让界面变成裸样式; 有脚本专门拦截这种遗漏 
- 字体分两档: UI 文字用系统无衬线栈, 代码块, 终端与需要对齐的数字用自托管等宽字体; 数字类展示打开等宽数字特性, 位数变化时不会左右跳动 
- 全站只有一个入场动画, 其填充模式必须是 backwards: 用 both 会让动画把变换留在效果栈里, 使主内容区成为定位基准, 页面内的浮层会相对整页而不是视口居中 
- 编辑器与正文的字体覆盖规则, 后台页内工具条的版式约定都集中在结构样式里, 视图不再各写一份; 分类与标签的配色由统一函数生成(后台配置的颜色优先, 否则按名称生成稳定色相), 只做弱提示不抢标题

### 6.7 前端模块注册表

前端与后端共用同一套模块 id 一个模块在前端声明导航入口(前台与后台)与页面路由, 由统一函数打上模块标记 路由表只保留布局自身的东西(首页, 登录页, 个人资料与后台重定向), 其余页面全部来自模块注册表 

- **路由守卫**: 目标路由带模块标记时先确保模块状态已加载, 模块不可用则送回首页 懒加载的页面组件在守卫之后才解析, 因此禁用模块不会下载它的代码 
- **导航与区块**: 侧栏入口由注册表生成并按模块状态过滤; 首页与详情页的模块化区块同样按开关决定是否渲染与请求 
- **纯前台模块**: 没有导航也没有页面路由的模块(终端卡片, 主页简介, 个人资料卡, 页脚, 网站链接, SEO, 看板娘, 代码块字体, 正文字号, 回到顶部)同样登记 id 与说明, 后台"模块管理"因此能一处看到"关掉会发生什么"; 它们的页面来自布局与首页, 自身不注册路由 
- 新增一个功能模块只需两处: 后端加模块包并登记, 前端在注册表加一条记录(需要页面就写路由), 之后由脚本核对两侧 id 一致 路由汇总, 布局组件与权限表都不应因为加功能而被改动

## 7. 关键功能实现

### 7.1 内容与阅读

- **文章状态与可见性**: 取值为草稿, 审核中, 已发布, 私密, 回收站 前台只展示已发布文章; 非公开文章的详情要求"作者本人或管理员"; 删除先进回收站可恢复, 彻底删除会连同评论与点赞一起删掉, 因此后台列表会返回评论数用于删除前提示 状态文案与标签配色在前端只有一处定义 
- **Markdown 渲染与高亮**: 后端只把 Markdown 转成带 class 的 HTML, 代码高亮, 复制按钮与超长代码折叠全在前端完成 高亮主题与深浅色联动; 未标注语言的代码块先按候选语言打分再决定是否上色, 避免误上色 
- **字数与阅读时间**: 中日韩按字, 英文按词, 用固定速度估算阅读时间, 由模型属性暴露给接口 前端保留同算法实现用于写作页的实时统计, 两处口径必须一致 
- **摘要**: 由作者手填, 不自动截取; 未填写则不渲染对应区域 
- **分类与标签**: 与文章都是多对多, 提交时整体覆盖; 颜色可在后台配置, 留空则按名称生成稳定兜底色, 保证同一分类全站同色 
- **文章目录与相邻文章**: 渲染正文时收集标题并补锚点 id, 右侧栏按层级展示并高亮"最后一个已滚过顶栏的标题", 窄屏改为正文上方的折叠块 相邻文章由详情接口一并返回, 只在已发布文章之间取 本站是 hash 路由, 锚点跳转不能靠改 hash 
- **归档与热门**: 归档一次性取回全部已发布文章并按"年-月"在服务端分组; 热门榜单按阅读量倒序且排序口径完全由后端决定, 首页与详情页共用同一接口保证一致
- **阅读增强**: 代码块字体, 正文字号与回到顶部由三个纯前台模块提供(codefont / fontsize / backtotop), 可在后台模块管理里单独启停, 并配置默认字号档位, 允许范围与按钮出现阈值 字号档位表固定在前端, 访客的偏好只写在浏览器本地, 不进数据库; 代码块字体必须靠外层类提高选择器特异性, 否则会被 Vditor 自带的字体声明压回去 

### 7.2 互动

- **评论**: 允许游客评论并记录 IP 与归属地, 支持多级回复(自关联), 可带图片与附件; 后台支持编辑, 审核状态与批量操作 删除一条评论必须连同它的回复一起删除, 只靠外键级联时回复会被置空父级而变成顶层评论 
- **点赞**: 切换式接口, 登录用户按账号去重, 游客按 IP 去重, 同时累加当日点赞统计

### 7.3 媒体

- **上传**: 按扩展名判定类型, 文件名用随机串, 按年-月分目录落盘, 返回可直接访问的地址 写作页, 媒体库与编辑器共用同一接口 单文件上限默认取环境变量, 可在后台按 MB 覆盖, 缺行或非法值时回退默认 
- **在线预览**: 渲染方式由纯函数按媒体类型与扩展名判定 - 图片, 视频, 音频直接渲染; PDF 交给浏览器内置阅读器; 文本类读取后用等宽块展示且有大小上限; 其余只提供下载 浮层支持遮罩与 Esc 关闭, 方向键在当页媒体间切换

### 7.4 统计与运营

- **访问统计**: 布局挂载与文章详情成功返回时埋点, 记录明细(IP, UA, 来源, 浏览器/系统/设备)并累加当日 PV, 当日新 IP 计 UV, 同时累加文章阅读量 按日聚合表是趋势图与贡献热力图的数据源 
- 累加阅读量时不能触碰文章的更新时间戳, 否则详情页的"最后更新于"会变成最后一次访问时间 
- **贡献热力图**: 按周或指定年份返回每天的发布数量(文章或日记), 前端用格子网格渲染; 首页是否展示由访问统计模块的 `show_on_home` 配置决定, 统计能力可以开而不占首页版面 
- **操作日志**: 关键写操作后记录操作人, 模块, 动作, 目标与 IP; 后台可按条件筛选 
- **后台看板**: 用一个聚合接口返回概览, 趋势与最新内容, 避免首屏发多个请求 区间与环比计算是纯函数, 视图只负责展示

### 7.5 集成与扩展

- **一言与历史上的今天**: 后端代理第三方接口, 上游地址与"每天只刷新一次"都是模块配置 一言按天缓存到系统设置里, 同一天所有访客共用一条, 上游异常时回退旧缓存避免页面空白; 模块被禁用后接口返回 404, 前台不再请求 一言与终端卡片互不依赖: 关掉一言后终端卡片保留, 只少最后两段输出 
- **首页区块与页脚**: 终端卡片(`session`), 主页简介(`about`), 个人资料卡(`profile`), 页脚(`footer`), 网站链接(`sitelinks`)与 SEO(`seo`)是设置项插件化后新增的纯前台模块, 内容与开关都在模块配置里 公开接口只下发"已启用模块"的配置, 因此关掉一个模块后前台连它的内容都拿不到, 页脚这类区块再叠加一层"内容为空则不渲染" - 页脚里的版权与备案各判各的, 只填备案也会渲染 网站链接卡片是否展示同样由模块状态决定: 可见范围配成公开时所有访客都能看到它在首页右侧, 配成仅管理员时只有管理员看得到 SEO 模块启用时向前台注入 meta keywords(取模块配置)与 meta description(取站点设置里的 `site_desc`, 它同时是 RSS 的订阅摘要) 
- **RSS 与 sitemap**: 用生成库产出订阅源与站点地图, 绝对地址由站点地址配置拼接, 订阅条数是模块配置 这两个路径挂在根路径而不是 API 前缀下, 因此按"根路径模块"装配 
- **站内搜索**: 对已发布文章的标题, 摘要与正文做模糊匹配并支持时间区间 通配符前缀会让索引失效, 因此当前实现不依赖全文索引, 数据量增长后需要重新评估检索方案 
- **导入导出**: 文章与日记共用两层 - 公共工具(frontmatter 解析与生成, 压缩包内图片落盘与正文地址改写)与导入管线(拆包, 解析, 查重, 落库, 写日志), 各业务只注入自己的解析规则, 查重键与落库动作 导入前先查重并返回结果, 由用户选择"跳过重复"或"全部导入"; 导出会带上正文引用到的本地图片以便再次导入

### 7.6 安全边界

- **API 文档鉴权**: 文档与开放接口描述路径要求管理员身份, 令牌来源为请求头或专用 cookie; 缺少令牌返回未登录, 身份不足返回无权限 权限判断同样只看权限码 
- **模块可见范围**: 配成"仅管理员"的模块, 它的接口在"模块是否启用"之后再加一层可见范围依赖(未登录 401, 已登录但无 `setting:manage` 403), 前台也不会收到它的入口与配置 未登录与无权限返回不同状态码, 与文档鉴权, 受控静态资源保持一致: 前者是"你还没有身份", 后者是"你的身份不够" 
- **静态资源访问控制**: 上传目录只放行浏览器会直接渲染的媒体类型(正文配图, 站点图标与头像必须匿名可访问), 其余扩展名与迁移数据目录要求管理员身份 公开的扩展名白名单直接复用上传校验的那一份, 避免两处各写一份而漂移 文档与静态资源两处的令牌来源, 失败状态码与权限判断必须一致, 因此共用同一段实现 
- 前端登录或恢复会话时把访问令牌写入专用 cookie, 登出或失效时清除, 这样后台的文档入口与页面内的图片, 下载链接都能直接打开而无需在地址上带令牌 反向代理必须透传该 cookie

### 7.7 看板娘

- 运行时与模型自托管, 运行时不请求任何外部地址 上游把模型基址写在运行时里且部分形象的纹理清单为空, 本地化时改回站内基址并补齐纹理路径, 具体改动记在该资源目录的说明文件里 
- 形象清单是一份数组, 新增形象只需放入模型目录并追加一条(可选单独指定画布尺寸, 全身像需要更高的画布) 
- 开关, 形象与位置存在本地存储; 全站总开关就是 `kanbanniang` 模块的开关, 关掉后侧栏控件与浮层一起消失, 连运行时与模型都不会请求 
- 运行时与模型等首屏之后再加载, 不与页面自身的请求抢带宽; 窄屏不展示; 关闭时只隐藏不销毁(反复重建会消耗 WebGL 上下文配额); 缺少 WebGL 或加载失败时放弃展示, 页面其余部分不受影响

也可直接双击根目录 `start.bat`: 脚本会检查虚拟环境与依赖, 缺少 `.env` 时自动从示例复制, 然后分别启动前后端并打印访问地址 

### 9.2 生产部署要点

- 前端构建产物交给静态服务器; 产物里包含编辑器, 看板娘与字体等按需加载的资源, 不要裁剪 静态服务器应开启 gzip 或 brotli, 体积用内置脚本测量而不是估算 
- 后端独立部署并关闭调试模式; 反向代理转发 API, 静态资源与(如需)文档路径; 前后端不同域时把前端域名加入允许的跨域来源 
- 反代必须透传鉴权 cookie, 否则管理员自己也会打不开文档与受控静态资源 
- 生产必须设置签名密钥(长度有下限), 应用会拒绝用占位值启动; 部署在反向代理之后时把代理地址填入可信代理配置, 否则应用不采信转发头, 客户端可以伪造 IP 
- 保证离线 IP 库已下载, 否则归属地显示为空 上传目录建议由反代直出并关闭脚本执行权限: 上传虽已做扩展名白名单, 这仍是纵深防御的一层
- settings 表里现在只有三类键: 站点身份, 平台约束与模块配置(`module.<模块 id>.<配置键>`) 从更早的版本升级时, 旧的展示开关与展示内容要手工搬到对应模块的配置键上(项目不保留一次性迁移脚本, 也没有数据库迁移工具)

### 9.3 数据保留

访问明细, 已过期或已吊销的刷新令牌与操作日志都会随时间增长, 应用不会自动清理, 需要时按保留策略手工删除 趋势图与贡献热力图读的是按日聚合表, 不受访问明细清理影响; 访问明细与来源分布只反映保留期内的数据 

## 10. 开发约定

- 代码注释与文档统一使用中文, 注释说明"为什么"而不是重复代码本身 
- 接口统一返回 `{code, message, data}` 并统一分页结构, 前端只解包一次 
- 权限校验一律用权限码, 不要判断角色名 
- 新增数据库列时先改模型, 再写迁移 SQL 并登记; 应用启动会校验模型与库结构, 缺列拒绝启动 
- 新增能力优先做成模块(见 5.7 与 6.7) 模块自己的配置项用模块配置声明, 不要再往站点级设置里加键 - 站点级只剩站点身份与平台约束 
- 视图里重复的流程逻辑抽到组合式函数, 视图之间的差异用 options 注入; 前端任何地方都不要直接写存储键字面量, 统一走令牌存储模块 
- 功能变更同步更新根目录 `CHANGELOG.md`(前台可展示给访客)
